# ChatData 查询类型分流状态更新

## 目标

梳理智能问数上层查询判定逻辑，避免明细查询和聚合分析查询混用同一套规则，降低大模型选字段后在校验阶段失败的概率。

## 当前状态

- 主链路已基本完成查询类型分流，不再属于“待设计”阶段。
- 当前生效口径：
  - 上层先区分：
    - 数据查询
    - 普通对话
    - 无法处理/超出范围
  - 若为数据查询，再区分：
    - 明细查询
    - 聚合分析查询
- 当前代码实际支持：
  - 明细查询时，`metrics` 可承载原始字段/维度字段
  - 聚合查询时，`metrics` 承载聚合指标，`dimensions` 承载分组维度
- 当前主链路口径：
  - 普通对话：不进入 SQL/语义生成流程
  - 无法处理：直接解释原因并给出引导
  - 明细查询：`metrics` 优先放原始字段，`dimensions` 通常为空
  - 聚合分析查询：`metrics` 放聚合指标，`dimensions` 仅用于分组

## 已完成项

- 已明确并固化上层两层判定流程：
  - 第一层：判断是否为数据查询
  - 第二层：若为数据查询，再判断是明细查询还是聚合分析查询
- 已统一核心查询口径说明：
  - 普通对话：不进入 SQL/语义生成流程
  - 无法处理：直接解释原因并给出引导
  - 明细查询：走明细规则
  - 聚合分析查询：走聚合规则
- 已明确明细查询规则：
  - `metrics` 表示需要展示的原始字段
  - `dimensions` 通常为空，不承担明细展示职责
  - 优先输出表格类结果
- 已明确聚合分析规则：
  - `metrics` 表示聚合指标
  - `dimensions` 表示分组维度
  - 支持时间粒度、排序、limit、having、compare 等能力
- 主链路 prompt / schema / 代码口径已基本统一：
  - `metrics` 不再只限定为“必须从可用指标中选择”
  - `dimensions` 已明确为分组字段，不是明细展示字段
  - 示例和工具 schema 已与真实执行逻辑基本对齐
- 旧语义层主要残留口径已完成清理：
  - 历史 prompt / matcher 已与主链路核心规则对齐
  - 明细查询下 `metrics` 可承载原始字段
  - 时间粒度口径已统一兼容到 `time_grain`

## 剩余待办

- 继续评估是否需要增加一层字段归一化：
  - 标准名
  - 同义词
  - 常见别名
  - 大小写/空格容错
- 重新跑一轮 NL2DSL / Agent 端到端评估，确认历史问题是否已消失：
  - 简单查询是否仍会出现 `No semantic tool call found`
  - `filters` 准确率是否仍明显低于 `metrics` / `dimensions`
  - 若仍失败，再定位问题发生在 `metrics` / `dimensions` / `having` / `order_by` 哪一层
- 压缩 prompt，减少重复内容：
  - 保留关键分类规则
  - 保留少量高价值示例
  - 删除重复的工具调用、字段约束、时间过滤说明

## 建议后续顺序

1. 先重跑一轮端到端评估，确认当前真实失败模式
2. 再决定是否增加字段归一化容错
3. 最后按需要继续压缩 prompt

# ChatData 数据源组执行适配 TODO

## 背景

当前 `chat-data` 的数据模型默认是：

- 一个 `datasource` 对应一个物理库
- 语义配置（指标集）挂在单个 `datasource` 下
- SQL 生成和 SQL 执行默认绑定同一个 `datasource_id`

这套模型不适合“同构分库 + 统一语义”的场景。当前业务既有单库场景，也有同构分库模式：多个物理库表结构基本一致，但执行目标不同。模型生成 SQL 后，还需要再决定落到哪个具体数据源执行。

## 当前问题

- 前端当前只有“数据源选择”，没有“执行目标数据源选择”
- 对话模式默认把“生成 SQL 的依据数据源”和“执行 SQL 的目标数据源”视为同一个对象
- 语义配置当前挂在物理数据源下，不利于复用同一套组级语义
- 几百个机构库无法靠当前下拉选择器人工切换处理
- 后续如果涉及跨数据源批量执行，现有接口模型也无法承载

## 目标

- 将“语义建模对象”和“物理执行对象”解耦
- 统一引入“数据源组”作为上层查询对象
- 支持基于统一语义指标集生成 SQL，再路由到具体数据源执行
- 前端选择从“选数据源”升级为“选数据源组/指标集 + 选执行数据源”
- 为后续批量数据源执行、跨数据源对比预留结构空间

## 当前建议方案

### 方案主线

- 统一引入“数据源组”概念，代表统一业务域
- 所有查询入口都面向“数据源组”，不再直接面向物理数据源
- 语义配置挂在数据源组下，而不是挂在单个物理库下
- 物理数据源作为组成员，附带成员标识和业务标签
- SQL 生成基于数据源组的语义配置与模板 schema
- SQL 执行基于用户选定的目标数据源或目标组成员

### 数据源组统一模型

- 每个业务域都是一个 `datasource_group`
- 如果组内只有 1 个成员：
  - 等价于单数据源场景
  - 可自动执行该成员
- 如果组内有多个成员：
  - 等价于分库场景
  - 执行前需要识别或选择执行数据源，再路由到具体成员

统一后模型变为：

- `datasource_group`
  - 组级语义配置
  - 组级模板 schema
  - 成员列表 `members`
- `member`
  - 物理数据源
  - 对应成员标签信息
  - 执行连接配置

### 临时可落地方案：业务上下文识别成员标签，后端映射执行

- 不让 LLM 直接选择 `datasource_id`
- 让上层只识别并输出业务标签信息：
  - 成员名称
  - 成员关键字
  - 或其他可映射的成员标识
- 后端收到标签信息后，通过本地映射表做确定性匹配：
  - `业务标签 -> datasource_group member`
  - 如果唯一匹配，则执行
  - 如果零匹配，则返回“未找到对应执行数据源”
  - 如果多匹配，则进入多数据源处理逻辑或提示用户补充

该方案适合作为第一阶段过渡方案，能在不全面重构数据模型的情况下先打通“按组建模、按成员执行”能力。

### 生成与执行解耦

- 生成阶段输入：
  - `semantic_config_id` 或 `datasource_group_id + semantic_config_id`
  - 用户问题
- 执行阶段输入：
  - `sql`
  - `target_datasource_id`

### 前端交互建议

- 不再让用户直接在几百个库里选 `datasource`
- 改为：
  - 先选指标集（语义层）
  - 再选执行数据源
- 如果组成员很多，执行目标选择器需要支持：
  - 搜索
  - 树结构
  - 最近使用
  - 权限过滤

### SQL 编辑器建议

- SQL 编辑器统一采用：
  - 数据源组 = 编写 SQL 的上下文
  - 执行数据源 = 真正执行 SQL 的目标
- 左侧表结构树、自动补全、AI 生成 SQL 统一基于组级模板 schema
- 第一阶段仅支持：
  - 组上下文下单数据源执行
  - 不直接在 SQL 编辑器主路径支持多数据源并发执行
- 结果区第一阶段保持单结果模型，仅补充执行来源信息：
  - `datasource_group`
  - `target_datasource`
- 如果后续支持多数据源执行，结果模型升级为：
  - 第一层按 SQL 语句分组
  - 第二层按执行数据源展示结果

## 最小可行改造（MVP）

第一阶段先不全面重构 Builder / Dashboard，优先让对话问数链路可用：

- 先在后端引入数据源组概念
- 先引入“业务标签 -> 组成员”的映射关系
- 语义配置逐步迁移到组级
- 模型生成 SQL 时基于组级模板 schema / 语义配置
- SQL 执行时根据映射改用真实组成员物理库

适用前提：

- 各组成员数据源 schema 基本一致
- 语义配置可复用于同一数据源组内所有机构库

### 第一阶段推荐执行规则

- 用户问题中识别到唯一执行目标：
  - 直接映射到对应组成员执行
- 用户问题中未识别到执行目标：
  - 需要明确默认策略
  - 可选：报错要求指定执行数据源 / 使用默认数据源 / 使用用户上下文默认成员
- 用户问题中识别到多个执行目标：
  - 第一阶段建议先不要盲目执行
  - 可选：提示用户补充更准确执行目标
  - 如果业务必须支持多数据源执行，需要进入“多库执行 + 结果合并”方案

## 多机构执行说明

### 可行性

- “匹配到多个执行目标后查询多个组成员库”在技术上可行
- 但这已经不再是简单路由，而是“多库并发执行 + 结果合并”问题

### 明细查询

明细查询相对容易支持：

- 对同一 SQL 并发查询多个组成员库
- 将明细结果拼接返回

仍需处理：

- 全局排序
- 全局分页
- `LIMIT` 不能简单按每库分别限制后再拼接

### 聚合查询

聚合查询不能简单拼结果，必须二次合并：

- `SUM`：各库结果求和
- `COUNT`：各库结果求和
- `MAX/MIN`：各库结果再取极值
- `AVG`：不能直接平均平均值，需要基于 `sum/count` 重算
- `GROUP BY`：需要按分组维度再次归并
- `COUNT DISTINCT`：跨库最复杂，直接合并容易失真

### 第一阶段建议边界

- 唯一执行目标命中：支持
- 多执行目标命中：
  - 第一阶段建议默认报错或要求用户明确机构
  - 如果要放开，优先只支持：
    - 明细查询
    - 简单聚合（如 `SUM/COUNT/MAX/MIN`）
- 暂不建议直接支持：
  - `COUNT DISTINCT`
  - 复杂分页排序
  - 高复杂度跨机构汇总

## 结构改造待办

- 后端增加“业务标签 -> 数据源组成员”映射结构

  - 组级 schema 获取
  - 执行目标校验

## 数据源维护待办

  - 新建组

  - 设置组描述和业务标签
- 明确组成员如何维护：
  - 数据源加入组
  - 数据源移出组
  - 设置成员别名
  - 设置成员业务标签/匹配关键字
  - 设置默认执行成员
- 明确数据源与数据源组的边界：
  - 单个物理连接仍作为 `datasource`
  - 多个 `datasource` 归属一个 `datasource_group`
  - 语义配置后续挂在 `datasource_group`
- 明确 schema 维护策略：
  - 组级模板 schema 从哪个成员产生
  - 是否支持手工指定“模板数据源”
  - 成员 schema 漂移时如何告警
  - 成员 schema 与组模板不一致时是否禁止加入
- 明确同步维护能力：
  - 新增成员后是否自动拉取表结构
  - 批量刷新组内成员 schema
  - 批量校验成员与组模板的一致性
- 明确前端管理入口：
  - 数据源管理
  - 数据源组管理
  - 组成员管理
  - 模板 schema 查看与同步入口
- 明确删除影响：
  - 删除数据源时是否允许被组引用
  - 删除组时语义配置、看板、收藏、历史如何处理
- 明确权限口径：
  - 哪些人可以维护数据源
  - 哪些人可以维护数据源组
  - 哪些人只能查询不能维护

## 风险点

- 数据源组内成员分库之间可能存在 schema 漂移
- 指标表达式或表关系在个别成员库中可能失效
- 如果后续要支持跨数据源汇总，单库执行模型仍然不够
- 会话历史、收藏、看板面板当前都更偏向“绑定物理库”的模型，后续要统一口径
- 业务标签名称、简称、别名可能导致匹配歧义
- 如果将大量成员映射直接塞进 prompt，可能带来 token 膨胀和识别误差
- 多数据源执行后，结果合并准确性和性能会成为新的系统风险

## 建议实施顺序

1. 先定义“数据源组 / 组成员 / 执行目标”模型
2. 再打通对话问数链路的生成执行解耦
3. 再补 SQL 编辑器的组上下文与执行数据源双层模型
4. 然后补前端执行数据源选择器
5. 再评估 Builder / Dashboard 是否一起迁移
6. 最后再考虑跨数据源批量执行和结果合并

## 看板兼容方向

- 看板后续统一支持两种范围：
  - 组级看板：面向 `datasource_group`
  - 单数据源看板：面向具体 `datasource`
- 建议看板模型增加：
  - `scope_type = group | datasource`
  - `scope_id`
- 组级看板第一阶段先只支持：
  - 组级建模
  - 单执行数据源运行
- 后续再扩展组级面板执行策略：
  - `single`
  - `aggregate`
  - `compare`

# ChatData 长耗时查询异步化 TODO

## 背景

- 当前 SQL 执行主链路仍是同步 HTTP 请求
- 部分 SQL、辅助查询、智能体问数实际执行时间可能达到 10 分钟以上
- 同步接口容易受到网关超时、前端请求超时、浏览器连接中断影响
- 即使前端使用 SSE，超长时任务也不适合长期绑定单个请求连接

## 目标

- 将长耗时 SQL 执行改为“提交任务 + 后台执行 + 轮询/订阅结果”模型
- 辅助查询、SQL 查询优先完成异步化
- 智能体查询暂不纳入本阶段异步化改造，先保持同步体验
- 任务执行与 HTTP 生命周期解耦，避免 10 分钟以上请求直接挂在接口上

## 统一任务模型建议

- 引入统一任务实体，例如：
  - `query_task`
  - `query_task_event`
- 核心字段建议包含：
  - `id`
  - `task_type = sql | dashboard`
  - `conversation_id`
  - `datasource_group_id`
  - `target_datasource_id`
  - `status = pending | running | waiting_user_input | succeeded | failed | cancelled`
  - `progress_text`
  - `request_payload`
  - `result_payload`
  - `error_message`
  - `created_at`
  - `started_at`
  - `finished_at`
- 统一接口模型建议为：
  - `POST /query-tasks` 创建任务，立即返回 `task_id`
  - `GET /query-tasks/{task_id}` 查询状态与结果摘要
  - `GET /query-tasks/{task_id}/events` 查询事件流或增量日志
  - `POST /query-tasks/{task_id}/cancel` 取消任务

## SQL 查询异步化

- `execute-sql` 增加异步模式，或新增 `execute-sql-async`
- 前端提交 SQL 后只拿到：
  - `task_id`
  - 当前状态
  - 预估轮询间隔
- 后端工作线程/任务队列后台执行真实 SQL
- 执行完成后将结果写入任务结果表，不再要求原请求保持连接
- 结果建议拆分：
  - 页面预览结果
  - 完整结果集下载能力（后续可选）

## 辅助查询异步化

- Builder 编译 SQL 后，如果进入真实执行，也统一走异步任务模型
- 面板执行、批量辅助查询、收藏 SQL 执行都尽量复用同一套任务基础设施
- 前端结果区需要支持：
  - 任务中
  - 执行完成
  - 执行失败
  - 用户取消

## 智能体查询处理原则

- 智能问数当前先维持同步模式，不在本阶段改造成异步任务
- 原因：
  - 智能问数对连续反馈和即时响应更敏感
  - 如果改成任务提交后轮询，当前产品体验会明显变差
  - 现阶段先优先解决 SQL 查询、辅助查询的长耗时问题
- 后续如果确实存在大量 10 分钟以上的智能体查询，再单独设计方案

## 智能体异步预研方向

- 暂只作为预研项，不进入当前开发范围
- 后续若要实现，再评估：
  - 是否保留同步主路径，仅对超长任务降级为后台运行
  - 是否拆为 `conversation` 与 `run task` 两层模型
  - 是否保留 SSE 负责短时增量反馈，长任务再转异步
  - Human-in-the-Loop、checkpoint、会话历史如何与任务状态统一

## 执行层建议

- 不建议继续在 Web 进程内直接跑 10 分钟以上任务
- 建议引入后台执行器，例如：
  - Celery
  - RQ
  - Dramatiq
  - ARQ
- Web 接口只负责：
  - 创建任务
  - 返回 `task_id`
  - 查询任务状态
- Worker 负责：
  - 执行 SQL
  - 写入事件与结果
  - 处理取消和超时

## 第一阶段可落地范围

- 先改 SQL 编辑器执行为异步任务
- 再改辅助查询执行为异步任务
- 智能体查询保持现状，不在当前异步范围内
- 等 SQL / 辅助查询异步方案稳定后，再单独评估智能体长任务方案

## 风险点

- 长 SQL 在数据库侧未必支持真正中断，取消能力要区分“任务取消”与“数据库取消”
- 超大结果集不能直接完整塞进任务结果字段
- 如果任务队列与 Web 进程部署分离，需要统一访问会话存储、checkpoint 存储、业务数据库
- 智能体查询暂未异步化，超长智能体任务仍可能受同步链路超时限制

## 建议实施顺序

1. 先抽象统一 `query_task` 模型与状态机
2. 先落地 SQL 编辑器异步执行
3. 再落地辅助查询/面板执行异步化
4. 先补取消、结果下载、事件清理机制
5. 智能体异步化单独预研，暂不进入当前排期
