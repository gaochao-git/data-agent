# ChatData 执行链路说明

本文档只说明一件事：智能问数、SQL 查询、可视化查询，在 `HTTP` 数据源模式下，到底是谁在轮询。

## 1. 结论

- 智能问数：前端不轮询，对方任务结果由后端轮询
- SQL 查询：前端轮询我方后端任务，对方任务结果仍由后端轮询
- 可视化查询：前端轮询我方后端任务，对方任务结果仍由后端轮询

也就是说：

- 是否轮询前端，只取决于当前页面模式
- 只要底层执行对象是 `HTTP` 模式，真正去查对方任务状态的一直都是后端

## 2. HTTP 数据源的后端执行方式

`HTTP` 模式执行器在 [services/sql_executor.py](./services/sql_executor.py) 的 `HiveHttpExecutor.execute()`。

后端行为如下：

1. 先调用对方提交接口，发送 SQL
2. 对方返回远端任务 ID
3. 后端继续调用对方状态接口
4. 后端循环轮询，直到成功 / 失败 / 超时
5. 后端拿到最终结果后，再返回上层

所以：

- 对方平台是异步任务模型
- 我方后端对它采用“提交后轮询”的方式

## 3. 智能问数

智能问数走对话链路，不走前端 `query-tasks` 轮询。

执行过程：

1. 前端发起智能问数请求
2. 后端生成 SQL
3. 后端直接执行 SQL
4. 如果底层是 `HTTP` 数据源，后端内部轮询对方结果
5. 后端拿到最终结果后直接返回前端

所以智能问数的表现是：

- 前端等待后端返回
- 前端不自己轮询任务接口

## 4. SQL 查询

SQL 查询走“异步任务”模型。

执行过程：

1. 前端调用 `POST /query-tasks`
2. 后端立即返回 `task_id`
3. 前端轮询 `GET /query-tasks/{task_id}`
4. 后端后台执行 SQL
5. 如果底层是 `HTTP` 数据源，后端在任务内部继续轮询对方结果
6. 任务完成后，前端从我方任务接口拿到最终结果

所以 SQL 查询是两层：

- 前端轮询我方后端
- 后端轮询对方平台

## 5. 可视化查询

可视化查询和 SQL 查询一样，也走 `query-tasks`。

区别只是 `query_type = builder`，执行模型不变。

执行过程：

1. 前端先编译 builder 配置得到 SQL
2. 前端调用 `POST /query-tasks`
3. 前端轮询 `GET /query-tasks/{task_id}`
4. 后端后台执行 SQL
5. 如果底层是 `HTTP` 数据源，后端继续轮询对方结果
6. 前端从我方任务接口拿到最终结果

## 6. 一句话记忆

- 智能问数：前端等后端直接返回
- SQL / 可视化：前端轮询我方任务
- 只要是 HTTP 数据源：后端轮询对方
