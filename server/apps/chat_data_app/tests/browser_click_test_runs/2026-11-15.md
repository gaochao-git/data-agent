## 4. 缺陷 DEF-2026-11-15-01：新任务压缩卡仍全堆末尾（回归）

**现象**：21:18 跑的「语义文件读取10遍统计」任务（3 次压缩，修复后产生），`GET /api/chatdata/conversations/{cid}/subagent-tasks/{tid}` 返回 `result_meta.subagent_trail` 共 67 条，3 张压缩卡下标 **[64, 65, 66]** 连续堆末尾；浏览器过程视图里三张卡 y 坐标 -1296 / -1260 / -1224，正文被挤到后面。与用户此前截图一致。

**根因**：上一轮加的「防堆叠兜底」拿绝对下标做判断 `if index <= previous + 1: index = min(previous + 2, len(merged))`。真实场景里压缩记录顺序与锚点位置并不单调（第一次压缩的锚点已被后续压缩删掉 → 落末尾 64，第二、三次锚点分别在 26 / 49），于是 **26、49 被误判成「堆叠」强行推到末尾**，加上 `min(..., len(merged))` 截断，三张卡全部叠在 [64,65,66]。用真实数据离线复现旧逻辑，输出与持久化完全一致。

**为什么单测没抓到**：既有用例只覆盖「锚点分散 t2/t4/t6」与「锚点全部重复 t2」，没有覆盖「部分锚点失效 + 其余锚点在早期」这一真实形态。

**修复**：`subagent_trail.py` 用 `_trail_anchor_index`（找不到返回 -1）替代 `_trail_insert_index`；新增 `_compaction_targets` 按**目标位置升序**排列压缩卡，锚点失效时借用它之后最早的已知位置以保持发生顺序、全部失效时均匀铺在过程尾部；插入时按 `target + 已插入卡数` 补偿偏移，仅当**目标位置相同**才做防堆叠。新增两条回归用例（部分锚点失效、全部锚点失效）。

**修复验证**：用同一份真实数据重算 → 压缩卡下标 **[26, 28, 51]**，相邻间隔 `[2, 23]`，id 顺序 `c1/c2/c3` 保持；既有 `[4,9,14]` 与重复锚点用例断言不变。

> 存量已持久化的 trail 按用户 21:14 拍板**不做兼容/迁移**；本次修复只影响之后新跑的任务。
