chat-data 未来设计分层

2026-10-11 架构讨论定稿 · data-agent / chat-data 语义建模体系
数仓建模把数据做对（可信的表），语义建模把含义做对（可信的答案），两条链在智能体消费处汇合。

图中两种血缘：数仓层间的横向箭头 = 加工血缘（表→表，发生在上游数仓平台）；数仓层到语义模型的纵向连线 = 语义血缘（模型 ↔ 物理表/列，由挂载与编译关系显式化）——两段血缘在语义层接续。覆盖目标：全数据源 × 全层 × 全表都有对应语义模型——ODS 用生成基础模型渠道批量铺探索级（零人工），DWD/DWS/ADS 按主题域建认证级；探索级补齐字典/指标/关系/粒度并通过质量规则后升级认证级。

二、一份语义模型的四要素构成

业务元数据
枚举 / 同义词 / 单位、列与表的业务描述
落点：L2 数据字典（权威）＋模型内绑定副本
业务模型
表选择、字段绑定、维度声明、关联（join / 自关联别名）
落点：datasets + relationships，驱动 join 编译
业务指标
原子 / 派生 / 复合指标口径
落点：metrics，DSL → 确定性编译 SQL
业务知识
模型用途说明、别名、示例问题
落点：ai_context / business_notes，兼作路由依据
四要素之外贯穿一条质量闸门：check_yaml 工具 / 导入 preview / 管理端 quality-check 三入口同一套规则（单模型 25 条 + 跨模型 3 条）。

三、层路由规则（用户不选层，系统路由）

情形路由
用户 @ 显式指定模型使用指定模型（最高优先）
问业务口径（“上月销售额”）主题域内匹配认证级模型；同指标多层命中取最高层（ADS > DWS > DWD）
问明细下钻（“某天某渠道”）切到 DWD 明细模型换粒度重新编译
问原始记录 / 贴源探索SQL 旁路或 ODS 探索级模型（结果带「口径未治理」标注）
跨主题问题多模型组合 / 多查询，主题域边界不拦正式口径消费
配套约束：对外口径只在最高层定义一次（同名异式已被跨模型规则拦截）；business_notes 写清层归属与上下层关系，作为路由的确定性依据。

四、资产四层栈（与数仓加工分层正交）

L1 数据源
MySQL / Hive 等真实库表；数仓加工链路（ODS→DWD→DWS→ADS）的产物在此接入
Source layer
L2 配置元数据
表结构缓存、数据字典、表分组（分层标记 / 主题域）
Metadata layer · Data Dictionary
L3 语义层
业务模型 + 业务指标 + 业务知识；物化 runtime + 质量治理 + Ossie 导入导出
Semantic / Metrics Layer（governed）
L4 智能体使用
会话问数（@ 引用 → DSL → 确定性编译 SQL）、BI、数据大屏
Consumption layer · Semantic Layer for AI
两条正交的轴：数仓加工链路横向流动数据本体（把数据做对）；我们的四层栈纵向流动语义定义（把含义做对）。语义层只挂建模纪律完成的表：ODS 禁正式挂载、DWD 带粒度声明挂、DWS/ADS 主力。
